# AxonHubClient 产品设计

本文档记录 `AxonHubClient` 的产品定位、能力边界、接口分层、CLI 设计和当前实现状态，用于指导后续实现。

## 定位

`AxonHubClient` 是 Agent 管理 AxonHub 实例的标准化操作层。

它负责把外部已经获得、已经授权使用的上游 API endpoint、API key、支持模型等信息转化为 AxonHub 中的 channel、model、routing 和 usage 管理对象。

## 总体设计

`AxonHubClient` 只使用 Admin Token 模式：

- `auth login` 登录任意 AxonHub 实例，并把默认 session 保存到当前用户配置目录。
- 后续命令自动读取默认 session，不支持 profile。
- 主要请求 `/admin/graphql`。
- 少量公共状态接口可请求 `/admin/system/status`。

建议基础命令形态：

```bash
axonhubclient <resource> <action>
```

建议支持的通用参数：

```bash
--json        # 输出 JSON
--confirm     # 明确执行写操作；未传时默认 dry-run
```

默认原则：

- 读操作可直接执行。
- 写操作默认 dry-run。
- 涉及密钥、删除、禁用、轮换、批量变更时必须输出变更摘要。

## 能力分层

### 1. 资产盘点

让 Agent 先理解 AxonHub 当前状态。

候选命令：

```bash
axonhubclient auth status
axonhubclient auth whoami
axonhubclient channels list
axonhubclient channels get <id>
axonhubclient channels summary
axonhubclient channels tags
axonhubclient api-keys list
axonhubclient api-keys get <id>
axonhubclient api-keys quota <id>
axonhubclient api-keys templates
axonhubclient models list
axonhubclient models get <id>
axonhubclient models rules preview <id>
axonhubclient models rules unassociated
axonhubclient models fastest
axonhubclient usage overview
axonhubclient usage cost-by-channel
axonhubclient usage cost-by-model
```

建议 Python 接口：

```python
client.auth.status()
client.auth.whoami()
client.channels.list(...)
client.channels.get(channel_id)
client.channels.summary(include_archived=False)
client.channels.tags()
client.api_keys.list(...)
client.api_keys.get(api_key_id)
client.api_keys.quota_usage(api_key_id)
client.api_keys.profile_templates(...)
client.models.list(...)
client.models.get(model_id)
client.models.channels(model_id)
client.models.unassociated_channels()
client.models.fastest(time_window="day", limit=5)
client.usage.overview()
client.usage.cost_by_channel(time_window=None)
client.usage.cost_by_model(time_window=None)
```

### 2. 渠道管理写操作

这是 `AxonHubClient` 的关键管理能力。外部工具只需要产出标准结构或明确的目标 ID，`AxonHubClient` 负责用默认 dry-run、脱敏输出和强确认边界把写操作提交给 AxonHub。

候选命令：

```bash
axonhubclient channels import channels.json
axonhubclient channels import channels.json --confirm
axonhubclient channels create --type openai --name xxx --upstream-base-url xxx --api-key sk-xxx
axonhubclient channels create-many channels.json
axonhubclient channels reorder ordering.json
```

建议 Python 接口：

```python
client.channels.create(channel)
client.channels.bulk_create(channels)
client.channels.import_file(path, dry_run=True)
```

建议标准输入格式：

```json
{
  "name": "provider-name",
  "type": "openai",
  "base_url": "https://example.com/v1",
  "api_keys": ["..."],
  "supported_models": ["gpt-4o-mini"],
  "default_test_model": "gpt-4o-mini",
  "tags": ["cheap", "external"],
  "ordering_weight": 100
}
```

安全要求：

- 输出中所有 API key 必须脱敏。
- CLI 通过 `--api-key` 直接接收上游 API key，可重复传入。
- 批量导入必须先做重复检测，例如 name、base_url、type、tags 等。

### 3. 渠道验证

导入后需要自动检查渠道和 key 是否可用。

候选命令：

```bash
axonhubclient channels test <id> --model gpt-4o-mini
axonhubclient channels keys test <id> --model gpt-4o-mini
axonhubclient channels keys disable <id> --key sk-xxx
```

建议 Python 接口：

```python
client.channels.test(channel_id, model_id=None)
client.channels.test_api_keys(channel_id, model_id=None)
client.channels.sync_models(channel_id, pattern=None)
```

后续可扩展：

- 根据测试结果禁用失败 key。
- 对失败渠道打标签。
- 输出失败原因聚合。

### 4. 模型管理和同步

让 Agent 能把新增渠道中的模型纳入 AxonHub 模型体系。

候选命令：

```bash
axonhubclient models list
axonhubclient models create <model-id>
axonhubclient models create-many models.json
axonhubclient models enable <id>
axonhubclient models disable <id>
axonhubclient channels models sync <channel-id>
```

建议 Python 接口：

```python
client.models.list(...)
client.models.create(model)
client.models.bulk_create(models)
client.models.set_status(model_id, status)
client.channels.sync_models(channel_id, pattern=None)
```

关键流程：

1. 获取 channel 支持的模型。
2. 对比 AxonHub 已存在模型。
3. 生成新增模型计划。
4. 用户确认后创建或启用模型。

### 5. 路由与成本优化

这组接口用于让 Agent 基于 AxonHub 内部数据辅助降低 token 消费。

候选命令：

```bash
axonhubclient routing inspect
axonhubclient routing suggest --goal lowest-cost
axonhubclient channels update <id> --input-json '{"orderingWeight": 100}' --confirm
axonhubclient channels tag <id> cheap
axonhubclient usage cost-by-channel --window 7d
axonhubclient usage success-rates --window 24h
axonhubclient channels status <id> enabled --confirm
axonhubclient channels archive <id> --confirm
axonhubclient channels recover <id> --confirm
```

建议 Python 接口：

```python
client.routing.inspect()
client.routing.suggest(goal="lowest-cost")
client.channels.update(channel_id, {"orderingWeight": weight})
client.channels.set_status(channel_id, "enabled")
client.channels.archive([channel_id])
client.channels.recover([channel_id])
client.channels.add_tags(channel_id, tags)
client.usage.channel_success_rates(time_window=None, limit=None)
```

优化建议应考虑：

- 成本。
- 成功率。
- 延迟。
- 支持模型。
- channel 状态。
- channel tags。
- ordering weight。

第一版可以只输出建议，不自动修改路由。

### 6. API Key 和敏感能力

API Key 管理属于高风险区域。

当前已实现渠道内 API key 状态管理，以及 API Key / Profile 主体的只读盘点：

- `api-keys list`
- `api-keys get <id>`
- `api-keys quota <id>`
- `api-keys templates`

这些只读查询不请求 API Key 明文字段 `key`。当前仍不实现：

- 显示 API key 明文。
- 复制 API key。
- 导出 API key。
- rotate API key。

后续如需实现，只允许：

- 默认脱敏输出。
- 创建后一次性显示必须由用户明确请求。
- API Key / Profile 主体的 rotate、删除、禁用等动作必须强确认；渠道内 API key 状态管理使用直接 key 参数、默认 dry-run 和高风险强确认规则。

## 实现里程碑

已完成的演进路径：

1. 建立 Admin Token 模式、REST 状态接口和 Admin GraphQL transport。
2. 补齐 `auth`、`channels`、`models`、`usage` 的只读资产盘点。
3. 补齐渠道主体写操作：导入、创建、更新、启停、排序、endpoint 保存、验证、模型同步、归档、恢复、删除。
4. 补齐渠道内 API key 状态管理：禁用、启用、启用全部、启用选中、清理 disabled key 记录。
5. 补齐 API Key / Profile 只读盘点：列表、详情、配额用量和 Profile 模板读取，禁止明文 key 输出。
6. 补齐 `requests` / `usage logs` / `traces` 运维排障只读命令，以及 `diagnostics channel-health`、`inventory summary` 和 `smoke read-only`。
7. 按 800 行文件上限完成 client、CLI、GraphQL query 和测试模块拆分，保留原有兼容导出。

下一阶段建议：

1. API Key / Profile 写操作按风险逐步开放。
2. `routing inspect` / `routing suggest`。
3. 项目、用户、角色和系统配置只读盘点。
4. 系统运维类高影响操作先补方案和风险分级。

后续写操作继续沿用当前规则：默认 dry-run，`--confirm` 才执行；高风险操作在 dry-run 输出中明确标记影响范围，输出不回显凭证。

## 当前实现状态

当前仓库采用 flat layout。`client.py`、`queries.py` 和 `cli.py` 保留为兼容门面，具体实现按资源领域拆分，避免单文件继续膨胀：

```text
axonhub_client/
  client.py                    # AxonHubClient 门面和资源 API 聚合
  client_admin.py              # auth、api-keys、channels、models
  client_observability.py      # usage、requests、usage logs、traces
  client_management.py         # diagnostics、smoke test、inventory
  client_utils.py              # connection/filter 辅助函数
  cli.py                       # CLI parser 和命令注册
  cli_handlers.py              # 写操作和复杂命令处理器
  cli_helpers.py               # JSON 输入、模型和渠道参数归一化
  cli_session_output.py        # session、登录和输出脱敏
  queries.py                   # GraphQL 常量兼容导出
  graphql_queries/             # 按领域拆分的 GraphQL query/mutation
  transport.py                 # REST / GraphQL transport
tests/
docs/
pyproject.toml
```

当前 CLI 入口：

```bash
axonhubclient <resource> <action>
```

首次使用通过 `auth login` 保存默认 session；session 文件位于当前用户配置目录，不保存密码：

```bash
axonhubclient auth login
```

实现安全约束：

- 渠道查询不请求 `Channel.credentials`。
- 渠道查询不请求 `disabledAPIKeys.key`。
- API Key 主体查询不请求明文字段 `key`。
- CLI 输出会对 `apiKey`、`apiKeys`、`key`、`token`、`password` 等常见敏感字段二次脱敏。
- `auth login` 不默认打印 token，且不会保存密码。
- 已实现 `channels create` / `channels create-many` / `channels import`，默认 dry-run；只有传入 `--confirm` 才提交 mutation。
- `channels create` 通过 `--api-key` / `--oauth-api-key` 直接接收凭证，可重复传入 `--api-key`。
- 已实现 `channels update <id>`，默认 dry-run；只有传入 `--confirm` 才提交 `updateChannel` mutation。CLI 通过 `--input-json` 或 `--input-file` 接收完整 `UpdateChannelInput`，因此调整权重不再需要单独的 `set-weight`。
- 已实现 `channels status <id> <enabled|disabled>` 与批量 `channels enable/disable`，默认 dry-run；只有传入 `--confirm` 才提交对应 mutation。归档和恢复使用 `channels archive/recover`。
- 已实现 `channels reorder`，默认 dry-run；只有传入 `--confirm` 才提交 `bulkUpdateChannelOrdering` mutation。
- 已实现 `channels endpoints set <id>`，通过 `--endpoints-json` 或 `--endpoints-file` 接收 `ChannelEndpointInput` 数组，默认 dry-run；只有传入 `--confirm` 才提交 `saveChannelEndpoints` mutation。
- 已实现 `channels test <id>` 和 `channels keys test <id>`，默认 dry-run；只有传入 `--confirm` 才提交测试 mutation。测试会真实请求上游接口，可能消耗上游额度。
- 已实现渠道内 API key 管理：`channels keys disable`、`channels keys enable`、`channels keys enable-all`、`channels keys enable-selected`、`channels keys prune-disabled`，默认 dry-run；单个或选中 key 通过 `--key` 直接传入。`keys prune-disabled` 属于高风险清理操作，执行时使用统一 `--confirm`。
- 未实现读取或展示 `disabledAPIKeys.key` 的命令；如需管理某个 key，调用方必须已经在外部合法持有该 key，并通过命令参数传入。
- 已实现 API Key / Profile 只读盘点：`api-keys list|get|quota|templates`。查询不选择 API Key 明文字段，`list` 默认排除 `noauth`，显式 `--type` 时按指定类型查询。
- 已实现 `channels models sync <id>`，默认 dry-run；只有传入 `--confirm` 才提交 `syncChannelModels` mutation。
- 已实现 `channels archive/recover/delete`，都支持一次传多个渠道 ID，默认 dry-run。删除属于不可逆高风险操作，执行时使用统一 `--confirm`。
- 建议优先使用专用命令完成常见渠道写操作；`channels update` 保留为高级通用入口，用于提交尚未被专用 CLI 包装的 `UpdateChannelInput` 字段。
- 已实现模型只读增强：`models get` 支持按实体 ID 或 `--model-id` 查询；`models rules preview` 默认读取模型 `settings.associations` 后调用 `queryModelChannelConnections`，也可直接传入 `--associations-json` / `--associations-file` 做预览；`models rules unassociated` 调用 `queryUnassociatedChannels`；`models fastest` 调用 `fastestModels(input)`。
- 已实现模型核心写操作：`models create`、`models create-many`、`models update`、`models status`、`models enable/disable/archive/recover/delete`。写操作默认 dry-run；`create` 只接收真实 `CreateModelInput` 且不接受 `status`；删除属于不可逆高风险操作，执行时使用统一 `--confirm`。
- 已实现模型关联规则接口：`models rules list <id>` 读取 `settings.associations`；`models rules replace <id>` 先读取模型现有 `settings`，只替换 `associations`，保留 `disableDeveloperSettingsInheritance` 等其它 settings 字段。`models rules add/remove/enable/disable/reorder <id>` 支持按 1-based 索引细粒度编辑，并自动把 `priority` 归一化为 `0..n-1`，保持 CLI 顺序与后端优先级一致。
- 已实现只读 `inventory summary`：复用渠道、模型、用量和成功率接口，输出渠道/模型状态分布、dashboard 概览、低成功率渠道、错误渠道、无 supportedModels 渠道、无关联模型和未关联渠道模型入口等关注项，供 Agent 先做实例盘点。
- 已补齐完整中文 CLI 参考：`docs/axonhubclient-CLI参考.md` 按资源整理命令、参数、安全确认和示例；`docs/examples/` 提供无真实凭证的 JSON 输入样例。
- 已将产品设计文档命名为 `docs/产品设计.md`，项目任务看板命名为 `docs/项目看板.md`；`docs/axonhub-探索笔记.md` 作为本地忽略笔记保留，不再纳入仓库管理。

## 与 Skill 的关系

Skill 是 `AxonHubClient` 项目的配套部分，用于指导 Agent 优先使用本项目提供的 CLI / Python client 管理 AxonHub，而不是把 `AxonHubClient` 视为 Skill 的附属代码。

浏览器工具只作为辅助：

- 获取或刷新 admin token。
- 对照 UI 验证接口行为。
- 当接口行为不明时观察前端请求。

常规管理动作应通过 CLI / Python client 完成，而不是手动点击后台页面。
